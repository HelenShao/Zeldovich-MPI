================================================================================
What could cause anti-scaling under mpiexec (besides thread binding)?
================================================================================
  - MPI runtime: progress thread or background threads (polling, async progress)
    can compete for cores or memory bandwidth even with no explicit communication.
  - Memory allocator: MPI may override or hook allocation (e.g. for registered
    memory); different allocation behavior can change locality or bandwidth.
  - Environment: mpiexec may set or unset env vars that affect OpenMP (e.g.
    OMP_PLACES, OMP_PROC_BIND) or the OpenMP runtime version/behavior.
  - Launcher placement: job launcher may assign a cpuset or NUMA policy to the
    MPI process; OpenMP may then bind relative to that in a way that worsens
    locality (e.g. threads spread across NUMA nodes) even if “binding” is set.
  - NUMA / first-touch: under mpiexec, initial thread or allocation placement
    can differ, leading to more cross-NUMA traffic as threads are added.
  - Different OpenMP runtime: MPI build might link a different OpenMP (e.g. KMP
    vs GOMP) or different FFTW/PLT libs that change threading behavior.

================================================================================
Changes to try with the toy (to fix or reduce anti-scaling under mpiexec)
================================================================================
  1. Cap z-loop threads (like production Z_LOOP_MAX_THREADS)
     In PBS or before mpiexec:  export TOY_ZLOOP_MAX_THREADS=4
     Then run with OMP_NUM_THREADS=16. Only 4 threads are used in the z-loop;
     if the slowdown is from too many threads on the shared buffer, time may drop.
     Try values 2, 4, 8 and compare Z-loop times.

  2. Parallel first-touch (NUMA)
     export TOY_FIRST_TOUCH=1
     The toy first-touches the buffer in parallel (same static schedule as the
     z-loop) so pages are faulted on the cores that will use them. Run with and
     without and compare.

  3. Launcher binding (run script only)
     Try explicit process binding so the single rank is pinned and OMP threads
     stay local, e.g.:
       mpiexec -n 1 --bind-to core ./toy_zloop_omp_scaling ...
     (Exact option depends on MPI: could be --bind-to core, -bind-to core, etc.)
     Or set in PBS:  export I_MPI_PIN=1  (Intel) or equivalent for your MPI.

  4. Explicit OMP placement (run script only)
     Try constraining threads to a subset of cores to reduce cross-NUMA traffic:
       export OMP_PLACES="{0,1,2,3,4,5,6,7}"
       export OMP_PROC_BIND=close
     Then run with OMP_NUM_THREADS=8 and compare to 16 threads on full node.

  5. Run 1 rank without mpiexec (if you add a no-MPI build)
     Build a toy that skips MPI_Init when not needed (or a separate no-MPI
     binary). For 1-rank “production-like” test, run that binary without
     mpiexec to see if scaling matches the current no-MPI single-process run.
